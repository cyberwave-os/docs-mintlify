## Overview

Edge drivers are built by **composing mixins** on [`BaseDriver`](/feature-reference/edge/drivers/base-driver-class) or [`BaseROS2Driver`](/feature-reference/edge/drivers/ros2-base-driver). Each mixin registers part of the MQTT catalog and supplies **seams** (methods you implement) for hardware-specific behavior.

Import the public surface from `cyberwave.driver`:

```python
from cyberwave.driver import (
    ArmCapabilityMixin,
    JointCommandBufferMixin,
    JointControllerMixin,
    TopicSpec,
)
from cyberwave.driver.ros2 import BaseROS2Driver, Ros2JointFeedbackMixin, Ros2TopicSpec
```

---

## Composition order (MRO)

**Method resolution order matters.** Put `JointControllerMixin` **before** `ArmCapabilityMixin` so joint targets from teleop and arm commands (`ee_move`, `grip`, …) both flow through `JointControllerMixin._apply_joint_targets`.

The Piper driver uses this exact stack:

```python
class PiperDriver(
    JointControllerMixin,
    ArmCapabilityMixin,
    Ros2JointFeedbackMixin,
    JointCommandBufferMixin,
    BaseROS2Driver,
):
    use_joint_controller = True
    use_joint_feedback = True
    use_base_commands = True
```

See [Reference pattern: Agilex Piper](#reference-pattern-ros-manipulator-arm-agilex-piper) for how `__init__`, `define_interface`, and `tick()` tie the mixins together at runtime.

## Mixin reference

| Mixin | Enable flag | You implement | SDK registers / provides |
| ----- | ----------- | ------------- | ------------------------ |
| **`JointControllerMixin`** | `use_joint_controller=True` | `joint_controller_config()`, `joint_controller_after_process()`; optional `joint_controller_motion()` | `joint/update` **listener** (`tele`, `edit`, `sim_tele`); shapes targets via `JointController.plan` |
| **`JointCommandBufferMixin`** | — (always compose for ROS arms) | `_init_joint_command_buffer()` in `__init__`, `_publish_joint_command()`, `_return_to_home()`, `tick()` → `pump_joint_commands()` | Thread-safe `CommandInbox`; teleop counters; optional `HOME_ON_TEARDOWN` |
| **`ArmCapabilityMixin`** | `use_base_commands=True` | `arm_config()` → `ArmKinematicsConfig` | `twin/command` listeners: `ee_move`, `ee_rotate_*`, `grip`, `release`, `home`, … |
| **`EECartesianPoseMixin`** | — | EE pose seams | Cartesian command extensions |
| **`DualArmMixin`** | — | `DualArmConfig` + per-arm routing | `left_*` / `right_*` commands on one twin |
| **`Ros2JointFeedbackMixin`** | `use_joint_feedback=True` | `joint_feedback_topic()`, `joint_name_map()`; optional `on_first_joint_feedback()` | ROS `JointState` subscription; `convert_joints_to_payload()` for `from_ros` |
| **`VideoStreamMixin`** | — | `_on_start_video_async()`, `_on_stop_video_async()` | `start_video` / `stop_video` commands and their status replies |
| **`CameraStreamMixin`** | `CAMERAS` or `CAMERA_SOURCE` (or subclass `BaseCameraDriver`) | optional `on_camera_frame(frame, camera)`, `on_camera_status(camera, status, reason)`, `push_h264()` for pre-encoded frames | Opens each camera, one WebRTC stream per camera with reconnect, `frames/<sensor>` and `depth/<sensor>` on Zenoh, frame filter, worker overlays, per-frame video sync data. Starts itself in `on_start_monitoring()`; a failing camera is retried without stopping the driver or the other cameras |
| **`AudioStreamMixin`** | — | Audio stream hooks | Microphone catalog |
| **`ZenohPublisherMixin`** / **`ZenohSubscriberMixin`** | — | Channel callbacks | Zenoh catalog entries |

### Control types (no mixin — used by mixins)

| Type | Role |
| ---- | ---- |
| `JointController` | Plans waypoint streams from target dicts |
| `JointControllerConfig` | Joint list, `passthrough_joints`, limits |
| `trapezoidal_motion` | Default motion generator |
| `JointNameMap` | ROS ↔ platform joint renaming (e.g. `gripper` → `joint7`) |
| `MotionGenerator` | Plug-in profile (`motion=None` = passthrough) |

See [Joint motion shaping](/feature-reference/edge/drivers/joint-motion-shaping) for shaped vs passthrough motion.

## Bidirectional `joint/update`

The `cyberwave/joint/{uuid}/update` topic carries **both** teleop commands and edge feedback. Split responsibility:

| Direction | `source_type` | Who registers it |
| --------- | ------------- | ---------------- |
| **Feedback** (ROS → MQTT) | `edge` | **Your** `define_interface` → `add_publisher(..., from_ros=Ros2TopicSpec(...))` |
| **Teleop** (MQTT → ROS) | `tele`, `edit`, `sim_tele` | **`JointControllerMixin`** — do **not** add a second `joint/update` listener |

Teleop listeners **reject `edge*`** messages so the driver never re-ingests its own feedback.

## Camera drivers

`CameraStreamMixin` streams a driver's cameras to the twin. Declare where the video comes from, one `CameraSourceConfig` per camera; the mixin does the rest.

Each camera is one `CameraSourceConfig`. Pick the factory for how the camera reaches the edge device:

| Camera | Declare | Video path | Driver image |
| ------ | ------- | ---------- | ------------ |
| USB (UVC / V4L2) | `CameraSourceConfig.usb(device_or_serial, camera_name)` | Captured and encoded by the SDK | standard |
| H.264 sent as RTP over UDP | `CameraSourceConfig.from_url("rtp://0.0.0.0:<port>", camera_name)` | Forwarded, no decode or re-encode | `-gstreamer` |
| IP camera with RTSP (H.264) | `CameraSourceConfig.from_url("rtsp://…", camera_name)` | Forwarded, no decode or re-encode | `-gstreamer` |
| IP camera, MJPEG/HTTP or H.265 | `CameraSourceConfig.from_url(url, camera_name, decode=True)` | Decoded by OpenCV, re-encoded by the SDK | standard |
| H.264 the vendor SDK hands over | `CameraSourceConfig.push(camera_name)` + `self.push_h264(frame)` | Forwarded, no decode or re-encode | `-gstreamer` |
| MPEG-TS over UDP or TCP | `CameraSourceConfig.from_url("udp://…" / "tcp://…", camera_name)` | Forwarded, no decode or re-encode | `-gstreamer` |

`camera_name` is the camera's sensor id on the twin. It names the WebRTC stream and the `frames/<camera_name>` Zenoh channel. Forwarded sources need GStreamer: `cyberwave[gstreamer]` plus the system plugins, which the `-gstreamer` driver image ships. Every frame carries video sync data when the `cyberwave-video-sync` extension is installed; set `VIDEO_SYNC_REQUIRED = True` to refuse to start without it.

### Connect a camera

#### A USB camera

The SDK opens the camera with OpenCV's V4L2 backend and encodes the frames itself.

```python
CameraSourceConfig.usb("/dev/v4l/by-id/usb-Acme_HD_Camera_0123ABCD-video-index0", camera_name="wrist_camera")
CameraSourceConfig.usb(serial_number="0123ABCD", camera_name="wrist_camera", resolution=(1280, 720), fps=30)
```

- **Name the physical camera, not its slot.** An index (`0`) or `/dev/videoN` moves when cameras are replugged or the host reboots, and a driver with one such camera falls back to any detected camera when it fails. A `/dev/v4l/by-id/…` link or the UVC `serial_number` pins the camera: the driver never substitutes another one. A serial is looked up under `/dev/v4l/by-id` each time the camera opens, so a camera plugged in later, or into another port, is found; until then that camera retries. Keep serials as strings (leading zeros).
- **Find the camera** on the edge host: `ls -l /dev/v4l/by-id/` (the serial is the field before `-video-index0`; use the `video-index0` node, the capture node), or `v4l2-ctl --list-devices`. A camera that reports no serial (the Logitech C920 is one) can be pinned by port with `/dev/v4l/by-path/…`.
- **Capture mode:** `resolution` must be a mode the camera offers (`v4l2-ctl -d /dev/video0 --list-formats-ext`). Without it the SDK's default (640×480) is used.
- **Give the container the device.** In `docker run` or `docker-compose.yml`, pass the node and the udev links, for example `--device /dev/video0` and `-v /dev/v4l:/dev/v4l:ro`. For a driver Edge Core runs, put the same flags in the twin's driver `params`.

#### An incoming RTP stream over UDP

For a camera, drone, or companion computer that sends H.264 as RTP to the edge device. The driver listens on the port and forwards the H.264 without decoding it.

```python
CameraSourceConfig.from_url("rtp://0.0.0.0:5600", camera_name="nose_camera")   # any interface
CameraSourceConfig.from_url("rtp://239.0.0.1:5600", camera_name="nose_camera") # join a multicast group
```

- **Sender:** H.264 in RTP, 90 kHz clock, to the edge device's address and this port, one port per camera. To test without hardware:

  ```bash
  gst-launch-1.0 videotestsrc is-live=true ! video/x-raw,width=1280,height=720,framerate=30/1 \
    ! x264enc tune=zerolatency key-int-max=30 ! rtph264pay config-interval=1 pt=96 \
    ! udpsink host=<edge-ip> port=5600
  ```

- **Keyframes:** the stream starts at the first keyframe; the driver waits `GST_KEYFRAME_TIMEOUT_S` (15 s) and then retries. Have the sender repeat SPS/PPS (`config-interval=1`) and send a keyframe every second or two, so a viewer that joins late gets a picture quickly.
- **Network:** on Linux, Edge Core runs drivers with host networking, so the container receives on the host's port; open it in the host firewall. Elsewhere (macOS, or a container on a bridge network) publish it: `-p 5600:5600/udp`.
- Only H.264 is forwarded. For H.265 or VP8, convert at the sender or use `push_h264()` from your own receiver. MPEG-TS over UDP or TCP works the same way with `udp://host:port` or `tcp://host:port`.

#### An IP camera

Most IP cameras and NVRs serve H.264 over RTSP. The driver pulls it over TCP and forwards the camera's own H.264, so a 4K camera costs no encoding on the edge device.

```python
import os

CameraSourceConfig.from_url(os.environ["GATE_CAMERA_URL"], camera_name="gate_camera")
# GATE_CAMERA_URL=rtsp://user:password@10.0.0.9:554/Streaming/Channels/101
```

- **The URL** is vendor-specific; check the camera's manual. Common forms: Hikvision `rtsp://<ip>:554/Streaming/Channels/101` (main) or `102` (sub stream), Axis `rtsp://<ip>/axis-media/media.amp`, Reolink `rtsp://<ip>:554/h264Preview_01_main`. Check it from the edge host with `gst-launch-1.0 rtspsrc location="<url>" ! fakesink` or `ffprobe "<url>"`.
- **Camera settings:** set the codec to H.264 (not H.265 or "H.264+"), and the I-frame interval to about one or two seconds. Prefer the sub stream when the main one is larger than you need: the driver forwards the camera's resolution and bitrate as they are.
- **Credentials:** keep them out of the code and the image. Read the URL from an environment variable as above; the driver redacts `user:password@` from logs and errors.
- **Decode instead** with `decode=True` when the camera serves MJPEG over `http://`, only H.265, or when you need worker overlays or the frame filter on this camera: OpenCV opens the URL and the SDK re-encodes the frames. This works on the standard image and costs CPU per frame.

### A camera driver

`BaseCameraDriver` is `BaseDriver` with the mixin wired in. The camera is the device: if it cannot be opened, the driver exits (code 66) before it reports ACTIVE.

```python
import os

from cyberwave.driver import BaseCameraDriver, CameraSourceConfig


class MyIpCamera(BaseCameraDriver):
    CAMERA_SOURCE = CameraSourceConfig.from_url(os.environ["CAMERA_URL"], camera_name="color_camera")


MyIpCamera.main()
```

Without `CAMERA_SOURCE`, the camera comes from the twin metadata Edge Core passes to the container:

| Metadata | Effect |
| -------- | ------ |
| `video_device` | Index, `/dev/video*` or `/dev/v4l/by-*` path, or stream URL. Default `0`. |
| `serial_number` | UVC: resolved to its `/dev/v4l/by-id` node. RealSense: pins that unit. |
| `is_depth_camera` | Overrides the depth mode derived from the twin's sensors (RealSense when true). |
| `resolution`, `fps`, `depth_fps` | Capture mode (`"WxH"`) and rates. Defaults: SDK resolution, 30, 30. |
| `gst_source` | GStreamer fragment that produces H.264 (for example `v4l2src device=/dev/video2 ! video/x-h264`). Forwarded without re-encoding. |
| `h264_passthrough` | With a stream URL as `video_device`: forward the camera's own H.264, using the same URL forms as `from_url`. |
| `frame_filter_enabled`, `frame_filter_freshness_ms` | Encode worker frames from `frames/filtered` instead of the capture; black when stale. Needs the Zenoh data bus and a source the SDK encodes. |

When a camera from metadata fails to open, the driver retries with the first detected camera, unless the configuration names one physical device (a serial, a `/dev/v4l/by-*` path, a URL or a GStreamer source). Override `on_camera_frame(frame, camera)` to edit raw frames before they are encoded.

### Several cameras

List them in `CAMERAS`, each with a `camera_name`. The name is the sensor id on the driver's twin; it names the camera's WebRTC stream and its `frames/<camera_name>` channel. The same driver can mix sources:

```python
from cyberwave.driver import BaseDriver, CameraSourceConfig, CameraStatus, CameraStreamMixin


class MyArmDriver(CameraStreamMixin, BaseDriver):
    CAMERAS = [
        CameraSourceConfig.from_url("rtsp://10.0.0.5/wrist", camera_name="wrist_camera"),
        CameraSourceConfig.usb(serial_number="0123ABCD", camera_name="base_camera"),
        CameraSourceConfig.push(camera_name="overhead_camera"),
    ]

    async def on_connect_to_device(self) -> None:
        arm_sdk.on_h264_frame(lambda frame: self.push_h264(frame, camera="overhead_camera"))

    def on_camera_status(self, camera: str, status: CameraStatus, reason: str | None) -> None:
        if camera == "wrist_camera" and status is CameraStatus.RETRYING:
            ...  # e.g. pause grasping until the wrist camera is back
```

Each camera runs on its own:

- It has its own stream, retry with backoff, and alert (component `camera/<camera_name>`). A camera that fails never stops the driver or the other cameras. With several cameras, the driver never substitutes a detected device for one that fails, because it could be another camera's.
- `on_camera_status(camera, status, reason)` reports `starting`, `streaming`, `retrying`, `stopped` and `failed` (a camera that cannot stream at all, for example with frame sync required but missing). `self.cameras` maps each `camera_name` to its stream, with `.status` and `.config`.
- `start_video` / `stop_video` apply to every camera, or only to the one whose `sensor` the command names.
- `push_h264(frame, camera=...)` names the push camera; you can leave `camera` out when the driver has only one.
- Worker detections are drawn on the camera whose `sensor` the payload names: pass `stream="<camera_name>"` to `model.predict()`. Detections that name no sensor are drawn only when the driver has a single camera, never on a guessed one. Workflow overlays (`frames/overlay`) name no sensor, so they are drawn on the first camera. The frame filter (`frames/filtered`) also names no sensor, so a driver with several cameras refuses to start with it enabled rather than stream the others unfiltered.

A `BaseCameraDriver` with several cameras activates as long as one camera opens, and retries the rest. It exits with code 66 only when none opens.

<Note>
  `CAMERAS` is for cameras that are **sensors of one twin**: the robot's asset declares them under its sensors, and they stream through the robot's driver. A camera modelled as **its own twin** (for example a child camera twin attached to an arm) gets its own driver: Edge Core starts one per camera twin. That driver is usually the stock camera driver, or a two-line `BaseCameraDriver`. See [Multi-camera driver orchestration](/feature-reference/edge/drivers/multi-camera-driver-orchestration).
</Note>

### Video from a robot driver

Compose the mixin with your own `BaseDriver` or `BaseROS2Driver`, for example in a bridge next to a vendor driver. It starts itself in `on_start_monitoring()` once the driver is ACTIVE, next to the base class's monitoring:

```python
from cyberwave.driver import CameraSourceConfig, CameraStreamMixin
from cyberwave.driver.ros2 import BaseROS2Driver


class MyRobotBridge(CameraStreamMixin, BaseROS2Driver):
    CAMERA_SOURCE = CameraSourceConfig.push(camera_name="front_camera")

    def connect_to_device(self) -> None:
        super().connect_to_device()
        robot_sdk.on_h264_frame(lambda frame, captured_at: self.push_h264(frame, capture_time=captured_at))
```

In a robot driver the camera does not decide the driver's fate:

- A stream that fails to open raises a camera alert and is retried with backoff (`CAMERA_START_RETRY_S`, doubling up to 60 s); the driver and its other cameras keep running.
- `start_video` / `stop_video` start and stop the stream without changing the driver's lifecycle state.
- The driver keeps its own `edge_health` heartbeat.

`push_h264()` is safe from any thread and never blocks; frames pushed before the stream opens are dropped. `capture_time` is the frame's capture time as `time.time()` seconds; it goes into the frame's video sync data. Omit it to use the arrival time. See `examples/h264_push_camera.py` and `examples/h264_passthrough_camera.py` in the Python SDK.

## Reference pattern: ROS manipulator arm (Agilex Piper)

The **[Agilex Piper driver](https://github.com/cyberwave-os/cyberwave/blob/main/cyberwave-edge-nodes/piper/public/cw_piper/driver.py)** (`PiperDriver`) is the canonical integration: five base classes, a handful of seams, and **one** `define_interface` publisher — no hand-written MQTT joint bridge.

### How the pieces connect

Mixins do not run in isolation. They wire together through **shared state** (`_joint_states`, `_tele_inbox`), **`super()` calls**, and the ROS **`tick()`** timer:

```mermaid
flowchart LR
  subgraph mqtt_in [MQTT in]
    JT[joint/update tele]
    TC[twin/command]
  end
  subgraph mixins [SDK mixins]
    JCM[JointControllerMixin]
    ACM[ArmCapabilityMixin]
    JBuf[JointCommandBufferMixin]
    RJF[Ros2JointFeedbackMixin]
  end
  subgraph ros [ROS graph]
    CMD[joint_ctrl_cmd]
    FB[joint_states_single]
  end
  subgraph mqtt_out [MQTT out]
    JE[joint/update edge]
  end
  JT --> JCM
  TC --> ACM
  ACM --> JCM
  JCM --> JBuf
  JBuf -->|tick pump| CMD
  FB --> RJF
  FB -->|from_ros| JE
  RJF -->|_joint_states IK| ACM
```

| Phase | What runs | Piper-specific |
| ----- | --------- | -------------- |
| **Class + flags** | MRO resolves mixin methods | `use_joint_controller`, `use_joint_feedback`, `use_base_commands`; `HOME_ON_TEARDOWN`, `EDGE_HEALTH_INTERVAL_S = 1` |
| **`__init__`** | Buffer + feedback init | `_init_joint_feedback()` then `_init_joint_command_buffer()` after `super().__init__` |
| **`configure()`** | ROS params, name map | `JointNameMap.from_arm_config(arm_config(), ros_to_platform={"gripper": "joint7"})` |
| **`define_interface`** | Catalog compile | `super().define_interface(iface)` registers mixin **listeners**; Piper adds **only** the `from_ros` **publisher** |
| **`register_callbacks`** | Extra ROS subs | Piper adds `arm_status` (vendor diagnostics — not part of mixin contract) |
| **`tick()`** | Executor timer | `pump_joint_commands()` drains inbox → `_publish_joint_command` |
| **Activate / teleop** | Operation mode | `on_enter_teleop_*` → enable service + CAN prime; **NO_OP** still streams edge feedback |

### Class declaration and flags

```python
class PiperDriver(
    JointControllerMixin,      # joint/update listener + planning seam
    ArmCapabilityMixin,        # twin/command (ee_move, grip, home, …)
    Ros2JointFeedbackMixin,    # ROS JointState → local _joint_states
    JointCommandBufferMixin,   # MQTT thread → ROS executor hand-off
    BaseROS2Driver,
):
    use_joint_controller = True
    use_joint_feedback = True
    use_base_commands = True
    HOME_ON_TEARDOWN = True
```

`JointControllerMixin` **must** precede `ArmCapabilityMixin` so IK-produced joint targets and MQTT teleop both enter `JointControllerMixin._apply_joint_targets`.

### `__init__` — wire mixin state

```python
def __init__(self, node_name: str, manifest_path: str | None = None, **kwargs):
    super().__init__(node_name, manifest_path, **kwargs)
    self._init_joint_feedback()       # Ros2JointFeedbackMixin
    self._init_joint_command_buffer() # JointCommandBufferMixin
```

Without these two calls the inbox, teleop counters, and `_joint_states` cache are never allocated.

### `define_interface` — feedback publisher only

`super().define_interface(iface)` lets mixins register `joint/update` **listener** and `twin/command` **listeners**. Piper adds the outbound path:

```python
def define_interface(self, iface) -> None:
    super().define_interface(iface)
    iface.add_publisher(
        TopicSpec(
            namespace="joint",
            leaf="update",
            payload_schema_ref="JointStatesPayload",
            rate_hz=30.0,  # JOINT_FEEDBACK_MQTT_RATE_HZ
            description="Edge joint feedback from joint_states_single",
        ),
        CallbackGroup(),
        operation_modes=frozenset(DriverOperationMode),
        protocol=ProtocolArgs(source_types=[SOURCE_TYPE_EDGE]),
        from_ros=Ros2TopicSpec(topic="joint_states_single"),
    )
```

At runtime `wire_ros_publishers()` subscribes on ROS, calls `convert_joints_to_payload` (uses `joint_name_map()`), throttles to `rate_hz`, and publishes with `source_type=edge`. **Do not** add a second `joint/update` listener — `JointControllerMixin` already owns teleop.

### Seam map — what Piper implements per mixin

| Mixin | Seam | Piper implementation |
| ----- | ---- | -------------------- |
| **`JointControllerMixin`** | `joint_controller_config()` | `joint1`–`joint7`; `passthrough_joints=("joint7",)` for gripper |
| | `joint_controller_motion()` | `return None` — Piper shapes velocity/effort in the ROS `JointState` cmd, not SDK trapezoidal |
| | `joint_controller_after_process()` | `lambda cmd: self.submit_joint_targets(cmd.positions)` → inbox |
| **`JointCommandBufferMixin`** | `tick()` | `self.pump_joint_commands()` |
| | `_publish_joint_command(positions)` | `ros_publish(cmd_topic, build_joint_command_msg(...))` with vendor vel/effort |
| **`ArmCapabilityMixin`** | `arm_config()` | `build_piper_arm_config(urdf_path=…)` for IK |
| **`Ros2JointFeedbackMixin`** | `joint_feedback_topic()` | `"joint_states_single"` (ROS param override in `configure`) |
| | `joint_name_map()` | `gripper` ↔ `joint7` via `JointNameMap` |

Command path end-to-end:

```text
twin.joints.set() / MQTT joint/update (tele)
  → JointControllerMixin._on_joint_target
  → JointController.plan (passthrough when motion=None)
  → joint_controller_after_process → submit_joint_targets
  → tick() → pump_joint_commands → _publish_joint_command
  → ros_publish("joint_ctrl_cmd", JointState)

twin.commands.ee_move() / grip / home
  → ArmCapabilityMixin IK
  → same JointController.plan path as above
```

Feedback path (two consumers, one ROS topic):

```text
ROS joint_states_single
  → Ros2JointFeedbackMixin._on_joint_feedback → _joint_states (IK, latch_gripper, prime)
  → from_ros forwarder → MQTT joint/update @ 30 Hz, source_type=edge
```

### Passthrough motion vs shaped

Piper returns `None` from `joint_controller_motion()` so targets pass straight through. Effort comes from the `joint_efforts` / `gripper_effort` ROS parameters; joint velocity does **not** — Piper has a single arm-velocity setting, `max_joint_velocity_rad_s` (rad/s), and every command is bounded by it. There is no per-command `speed` argument on Piper's `ee_move` / `ee_rotate_*`. Arms that need SDK-side smoothing return `trapezoidal_motion` instead — see [Joint motion shaping](/feature-reference/edge/drivers/joint-motion-shaping).

### Operation modes and edge health

- **`NO_OP`**: Piper resets the teleop inbox but keeps ROS lifecycle **Active** so `from_ros` feedback continues (`on_enter_no_op`).
- **Teleop**: `on_enter_teleop_local` / `remote` call vendor enable + CAN prime; commands flow only when hardware accepts them.
- **Liveness**: `_touch_edge_health()` on joint and arm-status callbacks; `edge_health` publishes at 1 Hz — no extra payload in `edge_health_extras`.

### What stays driver-specific (not mixin)

Piper still owns vendor glue that mixins do not cover: `managed_launch` (piper_ros), CAN setup, `/enable_srv`, `arm_status` subscription, and homing repeats on teardown (`HOME_ON_TEARDOWN`). Mixins handle the **Cyberwave contract**; the driver handles **hardware bring-up**.

### Client APIs vs driver plumbing

| API | Use |
| --- | --- |
| `define_interface` + `from_ros` | **Edge drivers** — ROS measured state → MQTT |
| `client.mqtt.update_joints_state(...)` | Scripts, sims, non-registry publishers |
| `twin.joints.set(...)` | **Application teleop** — commands only, not driver feedback |

End users call `twin.joints.set()` / `twin.joints.get()`; they do not implement `from_ros`.
